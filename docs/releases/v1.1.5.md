# v1.1.5: install scripts into a root-owned tree (fixes user-to-root privilege escalation via root cron)

## Summary

Up to v1.1.4 the installer downloaded the maintenance scripts into `$HOME/pi-scripts` as the
installing user and then registered those same paths in the **root** crontab. The files were
only `chmod +x`, never owned by root, and they source `lib/*.sh` from the same user-owned
directory. Anyone able to write as that user — a stolen SSH key, a malicious project, malware in
the desktop session — could overwrite `update_pi_os.sh` (or a lib) and wait for the next scheduled
root run: full host takeover, including the Gmail app password in `/etc/msmtprc`. No `sudo`
password was needed. Making the files root-owned inside `~` is not enough either, because the
home directory itself is user-writable, so the whole tree can be renamed and replaced.

Separately, `update_self.sh` defaulted `INSTALL_DIR` to `$HOME/pi-scripts`, which under root cron
is `/root/pi-scripts` — so the weekly self-update refreshed a copy root cron never executed and
left the live user-owned scripts untouched.

## What Changed

### 1. Root-owned install tree (`install.sh`)

- `INSTALL_DIR` now defaults to `/usr/local/lib/pi-maintenance`. Every write into the tree goes
  through `_install_run` (sudo when the tree is not writable, direct when already root) and files
  are placed with `install -o root -g root`: `0755` directories and scripts, `0644` `lib/*.sh` and
  `.version`. Atomic replace is kept (staged copy next to the destination + `mv`), so a running
  `update_self.sh` keeps its inode.
- `RECIPIENT_EMAIL` injection happens on the staged temp file before it lands in the root-owned
  tree; `save_email_configuration` rewrites installed scripts via `_install_run sed -i`.
- `INSTALL_DIR="$HOME/pi-scripts"` — what `update_self.sh` ≤ v1.1.4 exports when it runs the new
  installer — is redirected to the root-owned default, so existing hosts land in the right place
  on their first self-update. Any other explicit `INSTALL_DIR` is honoured; a user-writable one
  (tests) is written directly.
- `get_task_status` derives the schedule from the crontab line itself instead of assuming the
  command path starts with `$INSTALL_DIR`.

### 2. Automatic migration of legacy installs

- `_legacy_install_dirs` finds `$LEGACY_INSTALL_DIR` (default `$HOME/pi-scripts`) plus any
  directory a suite crontab line still points at. Both `install.sh --update` and the interactive
  entry re-download into `$INSTALL_DIR`, repoint the root crontab and the legacy owner's user
  crontab (Pi-Apps job) from the old directory to the new one, and delete legacy directories that
  contain **nothing but** suite files (`.version`, a `lib/` holding only the three helper libs,
  the seven scripts). A directory that also holds anything else — e.g. `/home/pi` referenced by a
  hand-written crontab line — is repointed but never deleted. Retirement only happens after the
  new tree was fully populated (`download_scripts` now returns non-zero on any failure, and
  `--update` / migration then abort without touching crontabs) and after the crontab rewrite was
  verified to no longer reference the legacy path.
- "Already installed" now also means "a legacy tree exists", so running the installer on an old
  host migrates first and then opens the manager menu.

### 3. `update_self.sh`

- `INSTALL_DIR` defaults to the script's own directory (`BASH_SOURCE`), never `$HOME`.

### 4. `uninstall.sh`

- Default path updated; removes the tree with `sudo` when it is not writable, and also removes a
  leftover legacy `$HOME/pi-scripts` — both only when they pass the same suite-only guard.
- Crontab-based directory detection actually works now: it reads the crontabs captured *before*
  the suite entries are stripped (previously it re-read them afterwards) and parses the script's
  directory from the command path instead of the line's last field (which was the `2>&1`
  redirect), matching any of the seven suite scripts. A directory (detected, default or legacy)
  is deleted only when it carries the installer's `.version` marker and every entry in it is a
  suite file, so a hand-written `/home/pi/update_pi_os.sh` line can never remove a home directory.

### 5. Tests and docs

- New `tests/install_root_owned.bats` (21 cases): default path, `$HOME/pi-scripts` redirect,
  override honoured, real root:root `0755`/`0644` ownership under an unwritable parent (uses
  passwordless `sudo` in a `mktemp` fixture, `skip`s without it), no-sudo direct writes for a
  user-writable tree, `--update` and interactive migration with crontab repointing, suite-only
  deletion guard (non-suite files, home-like dirs, non-suite `lib/` contents), abort paths when
  the download fails or a crontab still references the legacy path, failed-removal warning,
  uncreatable tree, legacy-path schedule parsing.
- `tests/uninstall.bats` (+8): root-owned removal via sudo, legacy tree removal, default path,
  detection from the pre-strip crontab capture (any suite script), refusal without the
  `.version` marker or with non-suite contents (install dir and legacy dir).
- `tests/component_tests_self_update.bats`: `INSTALL_DIR` defaults to the script directory even
  when a stale `$HOME/pi-scripts/.version` exists.
- Every installer/uninstall test entrypoint now isolates `LEGACY_INSTALL_DIR` so the suite can
  never migrate or delete a real `~/pi-scripts` on the host it runs on.
- README (security note + crontab examples), `docs/script_logic.md`, `Instructions.md`,
  `AGENTS.md`, Copilot instructions and skill playbooks updated.

## Breaking Changes

- Scripts move from `~/pi-scripts` to `/usr/local/lib/pi-maintenance`. The move is automatic on
  the next `install.sh` run or weekly self-update: crontabs are always repointed, and the old
  directory is deleted only when it contains nothing but suite files (otherwise it is left in
  place with a notice). Anything of your own that referenced `~/pi-scripts` needs the new path.
- Overriding `INSTALL_DIR` to a user-writable location reintroduces the vulnerability; only use a
  root-owned path.

## Notes

- Existing hosts pick this up on the weekly `update_self.sh` run (Sunday 01:00 by default). The
  old `update_self.sh` exports `INSTALL_DIR=/root/pi-scripts`; the new installer redirects that to
  the root-owned default, repoints the crontabs, and removes the stale copies.
