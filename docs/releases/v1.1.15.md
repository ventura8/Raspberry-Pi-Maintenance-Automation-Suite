# v1.1.15: Pin RAW_URL and INSTALL_DIR so env implants cannot hijack the installer

## Summary

Three security reports showed that `install.sh` trusted two environment variables that decide what
code runs before the first `sudo` and what root cron later executes:

- **`RAW_URL`** was taken from the environment with no allowlist. Same-UID malware exporting
  `RAW_URL=https://attacker.example/tree` (e.g. from `~/.bashrc`) made the documented `curl | bash`
  install, **Force Update Scripts** or `install.sh --update` `eval` attacker-hosted helpers and stream
  attacker scripts into the root-owned `/usr/local/lib/pi-maintenance` tree scheduled by root cron.
- **`INSTALL_DIR`** was also taken from the environment. Pointing it at a user-writable tree made
  `_install_src_trusted` skip its root-owned ancestor check, so a planted `lib/os_pkg.sh` defined
  `pkg_install` before `check_dependencies` prompted for the sudo password. Piped `uninstall.sh`
  likewise sourced `$INSTALL_DIR/lib/ui_msg.sh` with no trust check at all.

This release pins both, enforces HTTPS on every installer fetch, and refreshes the dependency pins.

## What Changed

### 1. RAW_URL pinning and HTTPS-only fetches (`install.sh`, `scripts/update_self.sh`)

- Outside `TEST_MODE`, an exported `RAW_URL` is honoured only when it is
  `https://raw.githubusercontent.com/ventura8/Raspberry-Pi-Maintenance-Automation-Suite/` followed by
  `main` or a `vX.Y.Z` release tag (what `update_self.sh` exports). Anything else prints a warning
  and falls back to the default before any `eval` or privileged install.
- Every installer `curl` (bootstrap libs, script/lib downloads, `VERSION`, manager Uninstall) uses
  `--proto '=https' --proto-redir '=https'`; the uninstall fetch now also fails on HTTP errors
  (`-f`). `update_self.sh` applies the same flags when staging the tagged installer.
- `update_self.sh` refuses a GitHub API `tag_name` that is not `vX.Y.Z` before building `RAW_URL`.

### 2. INSTALL_DIR pinning and strict helper trust (`install.sh`, `uninstall.sh`)

- Outside `TEST_MODE`, `install.sh` and `uninstall.sh` ignore an exported `INSTALL_DIR` and always
  use `/usr/local/lib/pi-maintenance`. Older installs in a custom directory that crontab still
  references are migrated like `~/pi-scripts`.
- `_install_src_trusted` no longer short-circuits for a writable `INSTALL_DIR` unless `TEST_MODE` is
  set, so helpers sourced before the first `sudo` always pass the root-owned ancestor check.
- `uninstall.sh` gains `_uninstall_src_trusted` and sources `ui_msg.sh` (sibling or
  `$INSTALL_DIR/lib`) only from a root-owned tree; otherwise it uses the inline stubs.
  `PI_UNINSTALL_ROOT_OVERRIDE` is honoured only under `TEST_MODE`.

`TEST_MODE` is itself an environment variable, so these gates are defense in depth against
env-only implants. Code that already runs as the login user can still shadow `sudo` via `PATH`;
the fixes close the paths where the suite itself handed that code root.

### 3. Regression tests

- `tests/install_extended.bats`: untrusted `RAW_URL` values (other host, `http://`, other branch,
  path traversal, other org) are rejected; a release-tag URL is honoured; exported `INSTALL_DIR` is
  ignored; planted `$INSTALL_DIR/lib` helpers are never sourced on a piped install; every installer
  `curl` carries `CURL_HTTPS`.
- `tests/uninstall.bats`: a planted user-writable `ui_msg.sh` is never sourced (piped or as a
  sibling), and a root-owned sibling `ui_msg.sh` still is.
- `tests/component_tests_self_update.bats`: a non-release API tag is refused before staging.

## Validation

- `./scripts/build-and-test.sh --full` (Docker lint, coverage gate, distro matrix compat + e2e).

## Breaking Changes

- `INSTALL_DIR=/custom/path ./install.sh` no longer installs to a custom location outside
  `TEST_MODE`; the root-owned default is always used.
- `RAW_URL` overrides pointing at forks or other hosts are ignored outside `TEST_MODE`.

## Upgrade Notes

No manual intervention is required. Existing installations update automatically via the scheduled
`update_self.sh` routine or via `install.sh --update`.
