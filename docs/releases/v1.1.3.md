# v1.1.3: fix fwupdmgr update detection when up-to-date devices are listed

## Summary

This patch release fixes a false "No updates available" in `update_pi_firmware.sh` on hosts that
use `fwupdmgr` (non-Raspberry Pi Linux). Modern fwupd (observed on 2.1.1) always prints a
`Devices with no available firmware updates:` section for devices that are current, *followed* by
a release block for any device that does have an upgrade. The previous check treated that header
as a "nothing to do" signal, so a pending release — for example the Microsoft UEFI dbx Secure Boot
revocation update (`20260402` → `20260707`, urgency High, seen on an ASUS NUC) — was reported as
"No updates available" and never installed. The release also carries the
`softprops/action-gh-release` 3.0.2 → 3.0.3 dependabot bump for the release workflow.

## What Changed

### 1. `fwupdmgr` update detection

- Detection now keys on the positive signal first: a release block containing `New version:` or
  `Release ID:` in `fwupdmgr get-upgrades` / `get-updates` output means an update is available and
  `fwupdmgr update -y --no-reboot` runs.
- Only when no release block is present does the script fall back to the legacy phrasing check
  (`No upgrades` / `No updates` / `No updatable devices`) for older fwupd versions.
- The `Devices with no available firmware updates` alternative was removed from the "no update"
  regex — it is printed on essentially every machine and can never mean "nothing to do".

Files:

- `scripts/update_pi_firmware.sh`
- `docs/script_logic.md`

### 2. Tests

- New BATS regression `fwupd mixed output (up-to-date list + pending dbx release) installs`
  replays the real output shape (verified against the affected host) and asserts that the install
  runs, a reboot is scheduled, and "No updates available." is **not** printed. This test fails on
  v1.1.2 and passes on v1.1.3.
- New BATS test `fwupd all devices current (no release block) does not install` guards the
  opposite case: the header alone with no release block still yields "No updates available." and
  no install/reboot.
- The shared `fwupdmgr` mock in `tests/setup_mocks.sh` now answers `get-upgrades` as well as
  `get-updates`, and its `update-avail` mode emits the realistic mixed output so the Samsung LVFS
  path is exercised against the same shape.

Files:

- `tests/component_tests.bats`
- `tests/setup_mocks.sh`

### 3. CI

- `.github/workflows/release.yml`: `softprops/action-gh-release` bumped 3.0.2 → 3.0.3 (dependabot).

## Validation

- `./scripts/build-and-test.sh --full` — lint-in-docker (shellcheck, shfmt, bash -n, line length,
  yamllint, actionlint, mdformat), coverage gate, and the full distro matrix: all green.
- The new detection logic was replayed against the real `fwupdmgr get-upgrades` output captured
  from the affected ASUS NUC (fwupd 2.1.1): the v1.1.2 logic reports "No updates available",
  the v1.1.3 logic reports an available update.

## Breaking Changes

- None.

## Notes

- Hosts already on v1.1.2 pick this up via the weekly `update_self.sh` run (Sunday 01:00 by
  default); the next firmware run after that will install any release fwupd was previously
  mis-reporting, and reboot if the update requires it.
