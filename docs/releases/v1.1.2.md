# v1.1.2: prefer msmtp for TLS-verified mail, seamless ssmtp migration

## Summary

This patch release closes a TLS certificate verification gap on Debian/Raspberry Pi OS mail
delivery. `ssmtp`'s legacy default configuration never enabled certificate validation, so Gmail
app-password authentication over STARTTLS was vulnerable to interception on a hostile network.
`msmtp` (which does verify the server certificate) is now the preferred mailer on every OS family.
A legacy `ssmtp.conf` that still holds live credentials (`AuthUser`/`AuthPass`) and has no usable
msmtp `account default` is migrated to `msmtp` automatically and silently on the next mail send
(backing up a non-empty incomplete `msmtprc` first); other existing `ssmtp` setups are left as-is.
The CI Docker matrix also picks up the same dependency bump that triggered this branch.

## What Changed

### 1. TLS-verified mail delivery (security)

- `write_mail_config` / `mail_sender_cmd` now prefer `msmtp` (verifies the SMTP server's TLS
  certificate via `tls_trust_file`) on every OS family, including Debian/Raspberry Pi OS, which
  previously defaulted to `ssmtp`.
- `lib/os_pkg.sh` installs `msmtp` (not `ssmtp`) for the `mail-transport` logical dependency on
  Debian family hosts. `msmtp-mta` is omitted from that install so apt/pacman cannot remove a
  working `ssmtp` (MTA Conflicts) before credentials are migrated; the suite calls `msmtp`/`ssmtp`
  directly.
- Where `ssmtp` must still be written (msmtp unavailable), the config now sets `TLS_CA_File` /
  `UseTLS=YES` best-effort, but this is **not verified to work**: Debian/Ubuntu's packaged
  `ssmtp` (2.65) does not recognize `TLS_CA_File` at all and performs no certificate validation
  whatsoever on that build, regardless of config. There is no `ssmtp.conf` setting that fixes
  this on that package — `msmtp` is the only mailer this project treats as capable of verified
  TLS, full stop.
- New `migrate_mail_config_to_msmtp()` runs at the top of every `send_mail` call: if a host has a
  legacy `ssmtp.conf` with live credentials, `msmtp` is already installed, and no usable msmtp
  `account default` exists yet, it reconfigures `msmtp` with the same credentials — no user action,
  no package installs from `send_mail` itself. On failure, the existing `ssmtp` config is left
  untouched (migration never rewrites `ssmtp.conf`; `TLS_CA_File` hardening only applies to
  configs written fresh by this suite). A non-empty existing `/etc/msmtprc` is backed up once to
  `/etc/msmtprc.pre-migration` before overwrite (plain `cp` when root; `sudo -n cp` otherwise;
  backup failure aborts migration without modifying `msmtprc`). Installing `msmtp` for hosts that
  only have
  `ssmtp` happens in the installer's `check_dependencies` path instead. Credential reads fall back
  to non-interactive `sudo -n cat` when direct access to `ssmtp.conf` yields empty
  `AuthUser`/`AuthPass` (common for mode-640 root:mail files under cron). Migration itself also
  requires root or passwordless `sudo -n` before writing `msmtprc`, so cron never hangs on an
  interactive sudo password prompt. User-crontab senders invoke `msmtp` via `sudo -n` when
  `/etc/msmtprc` is not readable (typical `640 root:mail`). Portless ssmtp `mailhub=host` values
  migrate to port 25 (ssmtp's default) instead of being rewritten to Gmail.
  `mail_read_recipient_from_config` prefers the msmtp default
  user over a leftover ssmtp address after migration.
- msmtp default-account resolution accepts spaced (`account default : parent`) and attached
  (`account default: parent`) inheritance syntax with **comma-separated** parent lists (msmtp’s
  rule; bare spaces are not separators); installer lookups go through `_msmtp_user_host`.
  A top-level `defaults` block alone is not treated as a usable `account default`
  (`msmtp --account=default` still requires that account). Defaults are snapshotted when each
  account starts, so a later `defaults` block cannot change an earlier `account default`.
  Generated `/etc/msmtprc` uses `syslog LOG_MAIL` instead of a umask-dependent `/var/log/msmtp.log`.
- Debian/Ubuntu Docker test images now install `msmtp` alongside `ssmtp` so the preference /
  package-mapping path is covered in CI (alongside Fedora/Arch/Rocky).
- **All migration/account-resolution test coverage now runs exclusively against real `msmtp`/
  `ssmtp` binaries**, not mocks. New `tests/e2e/e2e_mail_migration.bats` (35 scenarios) exercises
  every `migrate_mail_config_to_msmtp` branch — STARTTLS/implicit-TLS/plaintext/custom ports,
  missing `SSMTP_CONF`, empty/partial credentials, malformed mailhub, invalid port, msmtp binary
  absent, no passwordless sudo, root-invocation (`cp` vs `sudo -n cp`), root:mail-640 `ssmtp.conf`
  via the `sudo -n cat` fallback, skip-when-already-migrated, backup-then-migrate,
  second-migration-aborts — plus `mail_sender_cmd`'s three-way fallback (msmtp usable → ssmtp
  preferred → msmtp last-resort), `mail_read_recipient_from_config`'s ssmtp fallback, every
  default-account inheritance form (spaced/attached/comma-list/chained/defaults-block-only/
  defaults-declared-late/defaults-only-invalid/undeclared-parent/forward-reference/space-separated-
  invalid), and a full end-to-end run of the real `install.sh --update` entry point (piped from
  `/dev/null` to prove no code path can wait on interactive input) — matching exactly what
  `update_self.sh`'s unattended weekly cron re-exec does on a real Pi. Every scenario is
  cross-checked against real `msmtp --account=default -P` (pretend/no-network parse) as ground
  truth, not just our own resolver. Debian-family only (ssmtp isn't packaged elsewhere); skips
  gracefully when either real binary is absent. No live SMTP send against an external server is
  performed. The 21 mocked equivalents in `component_tests_os_pkg.bats` were removed — they use
  `cat`-stub binaries that accept anything, so they could not have caught (and did not catch) the
  `LOG_MAIL`/`mail` regression below.
- This effort also found and fixed a real production gap: `mail_read_recipient_from_config` called
  `_msmtp_default_field` directly, which had no `sudo -n` elevation fallback (only
  `_msmtp_has_default_account` had its own, separately duplicated one) — a mode-640 `root:mail`
  `MSMTP_CONF` unreadable by the invoking process (a real, common state: `usermod -aG mail` doesn't
  apply to an already-running session) made recipient lookup silently fail even though the mailer
  itself worked. Consolidated the elevation fallback into `_msmtp_default_field` so every direct
  reader benefits consistently.

## Validation

- `bats` mail/install/component suites (`component_tests_os_pkg.bats`, `install_interactive.bats`,
  `component_tests.bats`, `unit_tests.bats`, `install_extended.bats`, `install_whiptail.bats`,
  `component_tests_samsung.bats`, `component_tests_self_update.bats`) — 173/173 pass, including the
  firmware automatic-dependency install/failure cases (path-hiding so host `fwupdmgr` does not
  mask the mocks).
- `tests/e2e/e2e_mail_migration.bats` (35 scenarios, real deps only) run against installed `msmtp`
  1.8.32 and `ssmtp` 2.65 binaries — 35/35 pass, each cross-checked with real
  `msmtp --account=default -P`. Every non-obvious semantic claim (undeclared-parent rejection,
  comma-vs-space parent separators, `defaults`-declared-after-account not retroactive,
  `defaults`-only-block not usable, `syslog` facility token) was independently confirmed against
  the real binaries and their man pages before being asserted in a test. This run caught a real
  regression from an earlier, unverified fix (`syslog LOG_MAIL` had been changed to `syslog mail`,
  which real msmtp rejects outright — `LOG_MAIL` is the documented, correct facility token, per
  `man msmtp`); reverted in `lib/mail_send.sh`, this file, and `README.md`. It also caught the
  `mail_read_recipient_from_config` sudo-fallback gap described above.
- Full local CI parity: `./scripts/build-and-test.sh --full`.
- GitHub Actions and Docker base images audited against upstream latest releases; no other stale
  pins found.

## Breaking Changes

- None. Existing `ssmtp` installs keep working and are otherwise untouched — the new `TLS_CA_File`
  setting only applies to `ssmtp.conf` written fresh by this release (a new install or an explicit
  reconfigure), not to `ssmtp.conf` files already on disk from before this release. Automatic
  ssmtp-to-msmtp migration is a separate case: it writes an `msmtp` config (`tls_trust_file`, not
  `TLS_CA_File`), and only for a legacy `ssmtp.conf` with live credentials and no usable msmtp
  `account default`, on the next scheduled mail send; other existing `ssmtp` setups are unaffected.
